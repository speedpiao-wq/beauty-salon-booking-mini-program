## 初始化云数据库

首个体验版本会在发现数据库尚未初始化时自动执行一次幂等初始化。下面的手工方式作为故障排查备用：

1. 在开发者工具中找到 `cloudfunctions/initializeDatabase`。
2. 选择“上传并部署：云端安装依赖”。
3. 在云开发控制台对该函数执行一次云端测试，参数为：

```json
{
  "confirm": "INIT_XIUYA_V1"
}
```

4. 继续部署 `cloudfunctions/getBootstrap`、`cloudfunctions/getAvailability` 和 `cloudfunctions/createBooking`。
5. 重新编译小程序；首页显示“云环境已连接”即表示首轮接入成功，可以测试创建预约。

初始化函数是幂等的：检测到系统已经初始化后不会再次覆盖数据。

## 当前阶段：店主确认闭环

- 客人提交后，预约状态为 `pending`；店主接受后改为 `confirmed`，客人可在“我的预约”看到“白兰已接受您的预约”。
- 店主端与客人端使用同一个小程序和同一个云数据库，通过微信身份白名单进入不同页面，不另做一个独立小程序。店主权限使用 `admins` 集合逐账号管理，支持白兰和共同店主两个微信账号；每次确认、改期或取消都记录实际操作账号。
- 首位店主在界面中显示为“创始人”（内部角色 `super_admin`），可以邀请、审批、停用其他店主账号；共同店主使用内部角色 `owner`，可以查看和处理预约。系统不允许停用最后一个有效的创始人，避免所有人失去管理入口。
- 店主确认时同步写入 `notification_jobs` 和 `audit_logs`，以便追踪是否已创建、发送成功或发送失败。
- 店主和客人都可以取消待确认预约，即使预约时间已经过去；已确认预约仅在护理开始前允许取消。取消会写入 `appointment_events` 和 `audit_logs`，停止尚未发送的提醒任务，并删除该预约占用的 `appointment_slots`，让这个时间重新开放。
- 客人端统一使用左滑操作：待确认或已确认卡片左滑显示“取消预约”，后台都记录为 `cancelled_by_customer`；已取消卡片左滑显示“删除记录”，只从当前列表隐藏，历史和审计仍然保留。
- 已取消预约在取消满24小时后的下一次每小时任务中自动标记为归档，并从当前列表移入“历史记录”。云函数 `archiveCancelledAppointments` 不物理删除预约主记录，保留后续查询能力。
- 真正向微信会话发送服务通知，需要客人在预约动作中调用 `wx.requestSubscribeMessage` 明确同意，并在微信公众平台选定可用模板后由云函数发送。当前开关只记录提醒意愿，尚不等于消息已发送。到店提醒默认计划提前120分钟，后台以后可在60—120分钟范围内调整；若客人在预约前不足120分钟才下单，提醒任务改为尽快处理。
- 店主预约台支持按日、按周、按月和自定义日期查询客户名称、护理项目、预约时间与状态。v0.1.6 增加“全部 / 已预约 / 已取消”，默认全部；“已预约”包含待确认与已确认，“已取消”包含客人取消与店主取消。云端先筛选再分页，每页50条，避免只在已加载记录中筛选而漏查。
- 按周查询默认当前周，周一至周日；先选月份，再选完整周区间，例如2026年9月为“8/31～9/6（第一周）”“9/7～9/13（第二周）”。按月查询直接选年月，默认本月；按日和自定义保留日期选择。
- 创始人及受邀共同店主的首页展示最近5条待到店的已确认预约，仅显示客人称呼和预约日期时间；返回首页、下拉刷新或停留30秒后刷新。“查看全部”进入店主预约台；原有长按绿色品牌卡片的入口保留。普通微信不会收到店主预约摘要。
- 后续 PC 可视化看板继续复用同一套预约数据，再增加改期、手工录单、临时停约和提醒状态，不提前混入会员消费模块。

## v0.1.6 等待时间优化与验证边界

- 店主身份、预约列表及创始人账号管理数据合并到一次 `ownerAppointments/dashboard` 请求；共同店主不会收到账号管理列表。每次云端仍核验当前身份，不用本地缓存跳过权限检查。
- 首页已读取的公开护理项目在内存中复用5分钟，进入预约页不再重复读取项目；可预约时间不缓存，继续实时查云端。下一步与提交时的防冲突校验保留。
- `getAvailability` 并行读取独立配置，并行查询占用锁与停约时段，减少串行等待；没有更换云环境或增加付费配置。
- 同一开发者工具的3次对比中，预约控件观测可用时间由1096～1217毫秒降至761～805毫秒；可约结果的自动化端到端观测为1272～1419毫秒，不能宣称全流程稳定低于1秒。
- 优化后店主主请求482～493毫秒，可约查询563～682毫秒；其中服务器函数内部处理分别77～85毫秒、119～149毫秒。其余还包含传输、微信调用链路及函数外部开销，不能把差值全部归为网络或确定为冷启动。
- 自动化 `reLaunch` 包含工具路由等待，不代表人点击时的页面耗时。`analysis/page-ready-v16.json` 另记录从页面 `onLoad` 到就绪数据的时间，不含屏幕实际绘制。上述均不是手机 Wi-Fi/4G/5G 的真机测试或延迟保证。
- 补充的页面生命周期测量：可约结果就绪490～618毫秒；店主台分别462、1227、501毫秒，仍出现一次超过1秒的波动。这里的起点是页面加载，不是手指点击，不与前述端到端数值混用。
